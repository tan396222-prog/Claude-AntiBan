# 主机输入法与远端应用的原生输入体验

日期：2026-11-04。本文供维护者决定实现方向；先说明用户能获得什么，再列实验依据与需要接入的边界。

## 结论与用户体验

完整方案有可行路径：继续使用主机输入法、候选词和个人词库，让远端应用在自己的输入框内显示拼音、分词与组合文字，再把文字光标位置传回主机定位候选窗。

客机浏览器的关键链路已经通过独立实验。正式交付仍需实现三平台主机接入，并在 Claude Desktop 的真实编辑器中验收。可行性实验使用独立会话。后续实现和实际输入验收单独记录于[实施进度](../test-reports/2026-11-04-native-ime/progress.md)，该记录区分源码接入、构建和真实输入体验。

例如输入 `ni'hao` 时，远端输入框应原位出现带组合标记的文字；选中“你好”后只确认一次。按取消键撤掉未确认文字；移动文字光标或跨行后，下一次输入的候选窗应出现在新的输入位置。主机上的地址栏、设置表单和终端继续由各自的本地输入控件处理。

## 已验证的部分

实验使用当前 Linux 客机的 Chromium 156.0.8078.73、GTK 3、IBus 1.5.32；独立显示、会话总线和临时用户目录。软件包仅通过 apt 下载、校验和解压，没有安装进系统。输入内容均为固定测试文字。后续图形实验限制在 700 MiB 内存的独立服务中，服务退出时回收全部进程。

| 问题 | 实验结果 | 含义 |
|---|---|---|
| 拼音能否由远端输入框原位绘制 | `prefix suffix` 的光标处显示 `prefix ni'haosuffix`，产生真实组合输入事件 | 不需要覆盖远端输入框，也不依赖剪贴板来显示组合文字 |
| 确认时会不会重复输入 | 最终值为 `prefix 你好suffix` | 组合更新与提交可分别传递 |
| 已有选区能否替换 | “你好”选区被确认后的“是”替换 | 应用自己的编辑器负责选区操作 |
| 取消会不会留下拼音 | 撤销组合文字后恢复 `prefix 是suffix` | 本次无选区的取消场景通过；其他取消语义仍须验收 |
| 富文本与 emoji | 富文本内原位组合，最终得到 `rich text中🙂` | 普通输入框与浏览器富文本均有基础支持 |
| 光标坐标能否跨行变化 | 两个位置分别报告 `[242,734,0,54]`、`[302,790,0,52]` | 有实际文字位置数据，坐标需结合显示缩放转换 |
| 第一次聚焦是否立即有坐标 | 初始坐标为空 | 不能把最近点击位置当作精确光标位置 |
| 能否主动刷新坐标并避免字母重复 | 输入桥消费主机已处理的真实 `n` 按键，得到 `[332,614,0,52]`，原文仍为 `prefix suffix` | 值得采用“主机处理组合输入、客机消费相应按键”的同步方式 |
| 密码框是否沿用相同处理 | 组合文字未出现在密码框，输入类型提示也未返回有效值 | 必须单独识别安全输入状态；不能仅依赖输入类型字段 |

以上是客机输入链路实验。程序化聚焦和选区配合原生 X11 按键完成测试；没有冒充主机真实中文输入法的完整人工验收。结果、原型和重现方法见[实验记录](../test-reports/2026-11-04-native-ime/README.md)。

## 推荐的职责划分

主机输入法负责按键解释、候选词、选词、组合范围和确认。客机应用负责文本布局、选区替换及组合文字绘制。Cage 负责有顺序地传递组合输入，以及把客机坐标转换成主机屏幕坐标。

建议为浏览器用户和 Desktop 用户各自提供私有的 IBus 输入桥，与各自的显示和会话总线保持相同生命周期。控制通道沿已有认证服务与 SSH 传输，不创建公开端口。正式实现可以采用小型原生客机服务；实验中的 Python、GI 和完整 IBus 解压目录不代表产品必须引入同样的依赖集合。

现有 noVNC 链路继续承接画面、鼠标和普通按键。由主机输入法处理的按键进入组合会话后，由客机输入桥消费，促使应用刷新光标信息；组合文字通过输入法接口更新。这个顺序已在 Chromium 证明可行，生产实现还需验证候选翻页、修饰键、重复键和切换输入框时的并发行为。

三平台共用客机桥和输入会话协议；主机接入点分别验证：

| 主机 | 推荐接入点 | 本轮证据与范围 |
|---|---|---|
| macOS | AppKit 原生文本输入客户端，提供组合文字、选区及字符屏幕矩形 | 官方接口契约已查证；本机 WKWebView 实测 `EditContext` 为 `undefined`，原生接入尚未实现 |
| Windows | 原生文本输入控件或 TSF 文本存储，向系统提供文字范围的屏幕矩形 | 官方接口契约已查证；需要用实际 WebView2 宿主与系统输入法测试 |
| Linux | 原生 GTK 输入上下文，接收组合文字和格式，设置候选窗定位 | 官方接口契约已查证；本轮客机 GTK 实验通过，主机 Cage 原生窗口尚未接入 |

普通网页组合事件能提供文字更新，但不足以证明三平台的分词格式、替换范围和候选窗定位均满足完整目标。原生主机适配是推荐方向，三平台验收须分别完成。

## 必须在实现中保持的契约

- **输入目标与顺序。** 每次聚焦生成新的目标标识与组合会话，更新带递增序号；浏览器切标签、切应用、失焦和断连均终止旧会话。迟到的确认不得进入新的输入框。
- **确认语义。** 组合更新、确认和取消独立传递。普通按键路径与组合路径共用顺序，候选确认的回车不能又变成远端提交消息的回车。
- **字符范围。** 明确主机 UTF-16、IBus 字符索引和 UTF-8 字节偏移之间的转换，包含 emoji 与组合字符；不能直接复用字符串长度。
- **显示坐标。** 客机文字矩形转换时包含 2 倍显示像素、Desktop 缩放、画面适配、侧栏、窗口位置和主机屏幕缩放。零宽光标有效，零高或过期矩形不能当作可用定位。
- **输入格式。** 保留组合内的选中片段、光标位置和下划线；本次原型只发送整段下划线，尚未验证主机分词格式。
- **密码与数据范围。** 安全输入状态需要可靠识别。输入文字和周边内容不进入日志、诊断导出或持久存储；仅在活动输入会话中传递完成编辑所需的数据。
- **完成边界。** 接口成功应区分已收到、已交给活动输入上下文、已确认提交。失焦后不得盲目重试提交。

这些属于新的跨端输入契约，本文记录推荐方案，尚未把它们当作当前产品已实现的能力。

## 其他路线与未解决项

浏览器已有的调试控制通道可以发送组合文字；Linux 输入法桥则有机会让浏览器和 Desktop 共用同一套协议。Claude Desktop 4.4212.0 的隔离启动明确拒绝调试参数，应用资源校验也限制了替换测试资源，因此本轮没有通过调试通道测试其真实编辑器。正式实现应使用应用支持的 Linux 输入法入口，并在真实应用中验收。

辅助功能接口可作为补充坐标来源。实验中默认启用辅助功能状态仍未收到 Chromium 事件；显式开启渲染器辅助功能后收到普通输入框坐标与密码角色。富文本末尾部分事件返回零矩形，因此不能把该接口作为所有输入框精确定位的唯一依据。真实按键由输入桥消费的实验，为继续研究实时光标同步提供了更直接的路径。

本轮未覆盖主机真实中文输入法的候选翻页与分词格式、日本语/韩语、多显示器、不同缩放、编辑器自绘输入区域、切换焦点时的迟到提交、密码框完整行为，以及 Claude Desktop 真实输入框。要宣称“原生无感”，必须完成这些与产品支持范围相符的验收，不能只以 API 调用或客机实验通过为依据。

## 一手来源

以下资料查询日期均为 2026-11-04。实现方向是根据接口与本地实验作出的判断，不是资料对 Cage 的兼容承诺。

- [IBus Engine](https://ibus.github.io/docs/ibus-1.5/IBusEngine.html)：组合文字、提交、光标位置和按键处理接口。
- [Chromium 的 GTK 输入上下文实现](https://github.com/chromium/chromium/blob/main/ui/gtk/input_method_context_impl_gtk.cc)：组合文字及属性转换；光标位置在按键处理时传给 GTK，密码框使用简单输入上下文。
- [Chromium 的 Linux 输入方法实现](https://github.com/chromium/chromium/blob/main/ui/base/ime/linux/input_method_auralinux.cc)：从应用文字客户端获取光标矩形，并传给输入上下文。
- [AppKit 文本输入客户端](https://developer.apple.com/documentation/appkit/nstextinputclient)：组合文字、选区、替换范围和字符位置的主机契约。
- [Windows 文本范围位置接口](https://learn.microsoft.com/en-us/windows/win32/api/textstor/nf-textstor-itextstoreacp2-gettextext)：文本范围的屏幕坐标契约。
- [GTK 输入上下文](https://docs.gtk.org/gtk3/class.IMContext.html)与[光标位置](https://docs.gtk.org/gtk3/method.IMContext.set_cursor_location.html)：主机组合输入与候选窗定位接口。
- [EditContext 规范](https://www.w3.org/TR/edit-context/)：由绘制者提供字符矩形的浏览器输入接口；本机是否具备能力以探针结果为准。
- [AT-SPI 字符矩形](https://gnome.pages.gitlab.gnome.org/at-spi2-core/libatspi/method.Text.get_character_extents.html)：辅助功能坐标接口，其在 Cage 中的适用范围仍需实测。
